Realtime · Local-first · Collaborative Meeting Copilot

emeet

即時會議 Copilot，同步文件更新、會議記錄、與回覆建議

macOS 原生工具在會議中擷取麥克風與系統音訊，生成逐字稿，並以文件脈絡輔助使用者回應、追問、整理 notes/actions，以及導覽共同編輯中的 Google Docs。

Realtime 會中即時輔助

不是只等會後摘要，而是在對話還在進行時提供下一句回覆與追問。

Local 本地音訊與模型彈性

macOS 音訊擷取搭配本機 STT、Ollama 或 OpenAI-compatible endpoint。

Collaborate 文件共編脈絡

讀取 Google Docs 內容，並把會議 live notes 同步寫回文件。

Prompt 對話提示

使用 What should I say? 與 Follow-up questions 推進討論。

Product Interface

正在會議中：逐字稿、AI 提示與 Google Docs 共編同時發生

1

本機雙路音訊

麥克風與系統音訊分流擷取，先把「我說的」與「對方說的」分開，再進入轉錄管線。

2

會中逐字稿

100 ms PCM16 audio frames 送到 FastAPI backend，以 speech window 產生 final transcript，支撐即時提示與筆記。

3

下一句 / 下一問

按下 What should I say? 取得可直接說出口的回覆；按下 Follow-up questions 取得釐清需求、風險與責任的問題。

4

滾動式 notes/actions

系統根據新增 final transcript 更新 Meeting Notes 與 Next Actions，會議進行中就留下可追蹤紀錄。

5

可替換模型管線

STT 可切換 faster-whisper / mlx-whisper；助理模型可切換 Ollama、OpenAI-compatible endpoint 或 CLI provider。

6

Google Docs 共編

連接文件後讀取脈絡、更新 live notes，並只在使用者明確指令下執行可定位、單一步驟的文件操作。

Motivation

會議中的主要壓力發生在「當下」

多數 AI notetaker 解決的是會後整理；但關鍵壓力通常發生在會議中。對方要求時程、追問風險、請你改文件時，使用者需要立刻理解、回應、追問，還要讓共同文件同步更新。

emeet 的定位不是「另一個摘要工具」，而是把正在發生的對話轉成三種會中行動。

  • 即時：從最新逐字稿產生下一句回覆與下一個追問。
  • 本地：音訊在 macOS 端擷取，模型與供應商可依隱私、速度與成本切換。
  • 協作：會議脈絡連到 Google Docs，live notes 與 action items 跟著討論更新。

Core Claim

AI 會議輔助的價值，不在會後替你回憶，而是在當下幫你把對話推進下一步。

Design Considerations

低干擾、可控制、能落地

D1 · Realtime belongs to the current turn
回覆與追問要貼近最新幾句對話，不能等 30 秒摘要週期才出現。
D2 · Local-first by architecture
麥克風與系統音訊先在本機分流；STT/LLM provider 抽象化，保留本機與私有端點選項。
D3 · Collaboration needs shared context
會議常圍繞文件進行，因此提示、筆記與 action items 必須能參考 Google Docs 脈絡。
D4 · Prompts should be conservative
AI 只提供可說出口的草稿與追問，不猜日期、owner、預算或未確認承諾。
D5 · Edits must be bounded
文件修改只在明確語音指令下執行，限定可定位段落與單一步驟操作，避免失控改文。

Design Outcome

使用者不用離開會議節奏，就能取得回覆提示、追問方向、文件脈絡與可保存的會議紀錄。
