# macOS 會議輔助工具的模型供應商與自帶金鑰（BYOK）研究

## 執行摘要

就你的畢業專題而言，**可以，使用者絕對可以被允許選擇自己的模型並使用自己的 API key**，前提是你要圍繞著具備能力感知的供應商抽象層來設計 App，而不是把某一家供應商硬編碼進去。這對 **OpenAI、Anthropic、Google Gemini、Groq、Together、OpenRouter、Ollama 和 LM Studio** 來說都相當直接。主要的工程挑戰並不是「模型選擇」本身；而是各供應商在**即時音訊支援、工具呼叫語意、結構化輸出保證、上下文大小，以及延遲路徑**上有實質差異。對於具備**即時逐字稿 +「我該說什麼？」+ 後續追問 + 會議筆記 + 行動項目**的會議輔助工具，最強的一級託管選項是 **OpenAI** 和 **Gemini**，因為兩者除了文字工具與結構化輸出功能之外，也都記載了**即時或低延遲音訊路徑**。**Anthropic** 很適合長上下文分析、筆記和以工具為基礎的推理，但在此處檢視的官方文件中，它並沒有提出可與 OpenAI Realtime 或 Gemini Live 相比的一級即時音訊輸入路徑。**Groq、Together 和 OpenRouter** 作為速度、開放模型廣度或路由的選擇性通道很有價值，但它們不應該成為決定你整個系統的最低共同分母契約。**Ollama 和 LM Studio** 是可行的本機自帶金鑰（BYOK）風格後端，可用於隱私或離線展示，但最好把它們視為**本機推論目標**，而不是你的整套會議堆疊。**GitHub Copilot 是最大的邊界案例**：GitHub 現在已為 Copilot SDK/CLI 和企業 Copilot 介面記載 BYOK，但這些文件描述的是 **Copilot 產品、SDK 和 agent 工作流程**，不是給任意第三方 App 使用的單純通用消費者聊天 API。**OpenAI Codex 與 GitHub Copilot 屬於不同類別**：Codex 品牌工具和模型是真實存在的，其中一部分也能透過 API 存取，但它們針對的是寫程式最佳化，而不是會議輔助。 citeturn35view1turn35view4turn37view0turn37view1turn11view1turn11view2turn11view4turn7view4turn7view5turn18view7turn18view8turn26view6turn28view2turn28view3turn30view2turn30view3

由此可以得到一個實務結論：如果 App 的**主打展示**是「AI 會聆聽會議，並建議我下一句應該說什麼」，那麼你的預設架構應該是**以音訊優先，並採用原生即時供應商**，接著再在上層用**結構化輸出**疊加筆記與行動項目擷取。如果 App 的主打展示改成「使用者可以接入任何供應商」，你仍然應該維持**雙層設計**：針對具備特殊即時/音訊行為的供應商使用原生轉接器，其餘則使用通用的 OpenAI 相容轉接器。 citeturn35view4turn37view1turn11view1turn18view6turn18view7turn26view0turn26view7

## 直接供應商 API

**OpenAI API** 是最完整、最符合你使用情境的單一供應商。OpenAI 目前的文件涵蓋**函式呼叫**、**透過 SSE 串流**、用於較低延遲長時間工具工作流程的持久性 **WebSocket 模式**、使用 JSON Schema 的**結構化模型輸出**，以及一套橫跨請求式語音轉文字、串流轉錄、文字轉語音和低延遲語音轉語音工作階段的**音訊/語音堆疊**。OpenAI 目前的模型文件也揭露了大型上下文模型：官方模型總覽列出 **GPT-5.5** 與 **GPT-5.4** 具備 **100 萬 token 上下文視窗**，而 GPT-4.1 系列也記載了 **100 萬 token 上下文**與低延遲非推理行為。對會議輔助工具而言，這使 OpenAI 成為在同一供應商下結合**即時建議**、**結構化筆記**、**工具使用**與**高上下文通話後摘要**最直接的方式。 citeturn35view0turn35view1turn35view4turn37view0turn37view1turn36search11turn36search1turn36search5

**Anthropic Claude API** 特別擅長**長上下文分析、結構化筆記生成，以及以工具為基礎的助理**。Anthropic 的文件明確記載了 **SSE 串流**、**工具使用**、**結構化輸出**，以及在高階 Claude 模型上最高可達 **100 萬 token 的上下文視窗**，模型文件也描述了如 **fast** 和 **fastest** 這類比較性延遲分層。Anthropic 也記載了**細粒度工具串流**，用來在傳送大型工具參數時降低延遲。對你確切產品範圍來說，主要限制是音訊：此處檢視的官方頁面著重於文字、圖片、PDF、工具和結構化輸出，而 Anthropic 的 OpenAI SDK 相容頁面明確表示該相容層**不支援音訊輸入**。用產品語言來說，Claude 是很好的**分析/摘要通道**，但不是你**即時會議音訊通道**最乾淨的一線選擇。 citeturn7view3turn7view4turn9view2turn9view3turn7view5

**Google Gemini API** 是即時會議輔助工具相對於 OpenAI 的最強主要替代方案。Google 的 API 參考文件記載了**標準**、**串流**和**即時** API；**Live API** 明確被設計用於透過 WebSocket 進行**低延遲、即時語音與視覺互動**，並具備**工具使用**、**音訊轉錄**，以及客戶端/伺服器實作路徑。Gemini 也記載了使用 JSON Schema 的**結構化輸出**、**函式呼叫**，以及 **100 萬+ token 長上下文工作流程**。模型文件進一步描述了為**亞秒級原生音訊串流**最佳化的 Live 模型，而最新 Gemini 3.5 Flash 指南則記載了 **100 萬 token 上下文**、工具支援，以及 agentic/寫程式導向工作流程。最重要的注意事項不是能力，而是產品形狀：Gemini 同時有**檔案音訊理解**和 **Live API** 路徑，但 Google 明確指出標準 Gemini API **不適用於即時轉錄使用情境**，並引導開發者針對該需求使用 **Live API** 或 **Cloud Speech-to-Text**。 citeturn11view6turn11view1turn11view5turn11view2turn11view3turn11view4turn12view3turn12view4turn14view0

## 開放模型託管與本機後端

**Groq** 在你的優先目標是**速度**而不是最大化功能一致性時很有吸引力。Groq 記載了 **OpenAI 相容** API 介面、會公布 **token 速度**與上下文視窗的支援模型目錄，以及專用的**語音轉文字**和**文字轉語音**端點。如果你的會議輔助工具採用拆分架構，例如**一個服務負責 STT，另一個服務負責推理**，或是你想用超高速開放權重模型生成建議，這會讓 Groq 特別值得考慮。關鍵注意事項是 Groq 的**結構化輸出**文件明確表示，**結構化輸出目前不支援搭配串流和工具使用**；這正是會破壞過度通用抽象層的那種供應商特定邊界案例。 citeturn18view0turn18view1turn18view2turn18view3

**Together AI** 如果你想存取許多開源模型，同時又保留託管 API，會比 Groq 更廣也更有彈性。Together 記載了 **OpenAI 相容性**、**串流**、**函式呼叫**、受支援模型上的**結構化輸出**、帶有**上下文長度**與功能欄位的 serverless 模型目錄，以及**批次**與**即時音訊轉錄**和**文字轉語音**。換句話說，Together 可以為「使用者選擇任一受支援開放模型」這個故事涵蓋許多面向。問題在於能力是**高度模型特定**，而不是整個平台一致：你必須查詢或硬編碼每個模型的支援情況，而不是假設「Together 支援 X」就代表每個模型都支援。 citeturn18view4turn18view5turn18view6turn19search0turn19search2turn19search5turn20search1turn20search5turn20search13

**OpenRouter** 最適合被理解為**路由器與標準化層**，而不是單一模型家族。其文件表示它為數百個模型提供**一個 API**，支援**串流**、**標準化工具呼叫**、**相容模型的結構化輸出**、**包含音訊在內的多模態輸入/輸出**，以及跨上游的**供應商路由**。它也記載了 OpenRouter workspace 層級真正的**自帶金鑰（BYOK）**功能，也就是你的 OpenRouter workspace 可以優先路由到你自己的 **Bedrock、Vertex 或 Anthropic** 金鑰，再回退到 OpenRouter 的共享容量。對於「選擇任何模型」本身就是重點的展示來說，這很強大。重要注意事項是**模型與供應商相容性仍然重要**：OpenRouter 可以標準化請求形狀，但它無法神奇地讓每個上游模型在工具、結構化輸出或音訊方面都同樣出色。 citeturn18view7turn18view8turn18view9turn18view10turn18view11turn18view12turn18view13turn22search0

**Ollama** 是強大的隱私優先本機選項。其官方文件涵蓋 **OpenAI 相容性**、**工具呼叫**、**結構化輸出**、**視覺/圖片輸入**，以及可設定的**上下文長度**。Ollama 的上下文長度文件明確把預設值與可用 VRAM 連在一起，依硬體等級提供從 **4k** 到 **256k** 上下文的範例，並允許開發者在硬體許可時提高上下文長度。如果你想為重視隱私的使用者或離線展示提供「自帶本機模型」模式，這讓 Ollama 相當合適。限制在於，已檢視的 Ollama 文件集中於**本機文字/圖片推論**與相容層，而不是可與 OpenAI Realtime 或 Gemini Live 相比的一級會議語音堆疊。實務上，這表示 Ollama 最適合作為 **LLM 通道**，而轉錄和音訊 I/O 很可能來自其他地方。 citeturn26view0turn26view1turn26view2turn26view3turn26view4turn23search11

**LM Studio** 扮演類似角色，但它對本機伺服器與相容性的敘事特別明確。LM Studio 的文件強調帶有 **OpenAI 相容**與 **Anthropic 相容**端點的**本機 API 伺服器**、**工具使用**、**結構化輸出**、**有狀態聊天**、模型管理，以及每個模型可設定的**上下文大小**。其工具使用文件也提出一個對你的抽象層設計很有用的重要觀點：LM Studio 表示**所有模型都至少支援某種程度的工具使用**，但品質會因**原生**與**預設**支援而不同。這很好地提醒我們，「支援工具呼叫」在實務上並不是二元的；模型模板品質很重要。和 Ollama 一樣，LM Studio 作為**本機供應商目標**非常可行，但已檢視的文件並未把它呈現為專用的即時會議音訊平台。 citeturn26view5turn26view6turn26view7turn26view8turn26view9turn26view10turn26view11

這裡有三種站得住腳的架構觀點。**主流商用觀點**是從 **OpenAI 或 Gemini** 開始，因為即時語音是一級功能。**路由器優先觀點**偏好 **OpenRouter**，因為模型選擇和回退是產品的價值主張。**隱私優先的少數觀點**偏好 **Ollama 或 LM Studio** 加上一套獨立語音堆疊，讓使用者能把推論留在本機。這些觀點沒有哪一個不合理；它們優化的是不同結果。不過，對畢業專題而言，最可靠的路徑通常是**先做商用即時，開放/本機作為選配**。 citeturn35view4turn11view1turn18view7turn18view9turn26view6turn26view7

## GitHub Copilot 與 Codex

**GitHub Copilot 已不能再被簡化地視為「只能用單一模型」，**因為 GitHub 現在已記載 **Copilot 中支援的 AI models**、Copilot 客戶端中的模型選擇、**Copilot SDK**、**Copilot CLI BYOK**，以及**企業 Copilot BYOK**。GitHub 的 BYOK 文件表示 Copilot SDK BYOK 可以使用 **OpenAI、Azure OpenAI / Azure AI Foundry、Anthropic、Ollama、Microsoft Foundry Local，以及其他 OpenAI 相容端點**，而 Copilot CLI BYOK 明確支援 **OpenAI 相容端點、Azure OpenAI 或 Anthropic**，也包含**本機 Ollama**。GitHub 的企業 Copilot BYOK 文件也表示，管理員可以附加供應商金鑰，讓團隊能以 **Copilot Chat、Copilot CLI 和 VS Code** 使用偏好的 LLM 供應商。Copilot 的模型參考文件進一步記載，支援模型的可用性取決於**方案與客戶端**，而且該集合會隨時間變動。 citeturn28view2turn28view3turn28view7turn28view8turn32view1

我仍然**不**會把 GitHub Copilot 做為你的 macOS 會議輔助工具預設後端，原因是範圍邊界，而不是否認其能力。GitHub 自己的文件把 **Copilot integrations** 定義為從 **Teams、Slack、Linear、Azure Boards 和 Jira** 等工具觸發 **Copilot cloud agent** 的方式。GitHub 的文件把 **custom agents** 定義為 Markdown agent profile，用來為 Copilot 工作流程指定**提示、工具和 MCP servers**。GitHub 的 **cloud agent API** 被記載為 **Copilot Business 或 Copilot Enterprise** 的**組織**功能，而不是給消費者 App 使用的公開原始 chat-completions 端點。GitHub 的 **local CLI with Copilot SDK** 文件也明確列出限制，例如**單一使用者**、**僅限本機**、**不支援多租戶**，以及必須事先登入 CLI。GitHub 也表示 SDK 透過 **JSON-RPC** 與 Copilot CLI 溝通，而且許多互動式 CLI 功能不會以程式方式暴露。這表示 Copilot 是真實可用的，但它仍然是具有產品範圍 API 與預覽功能的 **Copilot 產品介面**，不是多使用者會議工具最乾淨的通用後端契約。 citeturn32view0turn28view5turn28view6turn34view1turn34view2turn28view2turn28view8

**OpenAI Codex 應該與 GitHub Copilot 分開看待。** OpenAI 的 Codex 文件把 **Codex CLI**、**Codex app**、**Codex web** 和 Codex models 描述為**寫程式 agent**。Codex 支援 **ChatGPT 登入**或 **API-key authentication**，進階設定文件也描述了具備可設定 base URLs 與驗證的**自訂模型供應商**。Codex 模型文件也顯示，**gpt-5.3-codex 這類 Codex 品牌模型具備 API access**，而且 Codex 可以指向任何支援 **Chat Completions 或 Responses APIs** 的模型/供應商。不過 OpenAI 自己的 `codex-mini-latest` 文件表示，該模型是**專為 Codex CLI 最佳化**，而對於直接 API 使用，OpenAI 建議從 **gpt-4.1** 開始。在你的專題中，這表示 Codex 在技術上可行，但除非你想加入與寫程式、repo 分析或開發者工作流程相關的附加功能，否則它是**問題錯位**的。它不是即時會議輔助的自然預設選擇。 citeturn30view4turn30view1turn30view0turn30view2turn30view3

對於以 Copilot 為基礎的會議資料路線，還有一個**授權與資料治理理由**需要謹慎。GitHub 的服務條款表示 GitHub 不主張擁有你的輸入或輸出，但對於 **AI Features**，GitHub 也表示個人授權使用者授予 GitHub 及其關係企業一項授權，可收集並使用輸入與輸出去**開發、訓練和改進** AI 系統，除非使用者選擇退出，或受到客戶協議或大量授權協議約束。同一節也表示輸出可能類似第三方程式碼或內容，並必須由使用者審查、測試和驗證。如果你的 App 會擷取可能敏感的會議逐字稿，這些條款就不是註腳；它們是架構決策的一部分。 citeturn34view0

## 自帶金鑰（BYOK）與供應商抽象層

從供應商文件得到的最重要架構教訓是，你**不應該**建立一個抹平所有供應商差異的假通用 API。OpenAI 有 **Responses**、**WebSocket mode**，以及獨立的**音訊/即時**敘事。Gemini 有**標準**、**串流**和 **Live API** 路徑。Anthropic 有 **Messages-style streaming**、**細粒度工具串流**和巨大上下文。Groq 的**結構化輸出**目前不能與**串流**或**工具使用**結合。OpenRouter 可以標準化請求形狀，但實際支援仍然**取決於上游模型**。GitHub Copilot SDK 根本不是原始網路 API；在一種已記載的模式中，它實際上就是一個透過 **JSON-RPC** 與 **Copilot CLI** 對話的客戶端。因此，好的抽象層必須是**能力感知**的，而不只是供應商名稱感知。 citeturn35view4turn11view1turn7view3turn7view4turn18view2turn18view10turn18view12turn34view1

對你的 App 來說，最乾淨的設計是拆分三個契約。第一個是用於聊天、建議和摘要的 **LLM 回應契約**。第二個是用於轉錄、語音轉語音或 TTS/STT 服務的**音訊契約**。第三個是**能力註冊表**，用來告訴 UI 與編排層，選定的 `(provider, model)` 組合是否支援**串流**、**工具呼叫**、**JSON-schema output**、**音訊輸入**、**音訊輸出**、**長上下文**，以及任何特殊注意事項，例如「不支援 structured+streaming」。這個註冊表應該驅動「我該說什麼？」按鈕是否能串流部分建議、「追問問題」是否能使用工具，以及通話後筆記是否能以經驗證的 JSON 輸出。 citeturn37view0turn11view2turn18view2turn19search0turn26view8turn26view9

務實的實作策略是：在供應商特定功能重要的地方使用**原生轉接器**，在不重要的地方使用 **OpenAI 相容轉接器**。實務上，我會為 **OpenAI**、**Gemini** 和 **Anthropic** 製作原生轉接器，因為它們最好的功能並不相同。接著，我會為 **Groq、Together、OpenRouter、Ollama 和 LM Studio** 製作一個通用的 **OpenAI 相容轉接器**，因為它們全都記載了直接 OpenAI 相容性或類 OpenAI 的請求形狀。這能讓你獲得廣泛的供應商覆蓋，同時不假裝每個端點真的都表現得一樣。 citeturn18view0turn18view6turn18view7turn26view0turn26view7turn30view0

自帶金鑰（BYOK）本身也應該以不只一種方式建模。**直接 BYOK** 路徑會把使用者的金鑰傳送到供應商端點。**路由器 BYOK** 路徑讓使用者提供 **OpenRouter key**，而 OpenRouter 自身可以再路由到 workspace 層級的下游 BYOK 供應商。**本機供應商路徑**可能完全不需要**雲端金鑰**，只需要 Ollama 或 LM Studio 的本機 base URL 與模型識別字。**GitHub/Codex 驗證則應該維持為獨立特殊案例**，因為 GitHub 的 BYOK 是預覽範圍內的 Copilot 介面，而 OpenAI Codex 支援不同的驗證/產品流程。試圖把這些全部壓平成一個「在這裡輸入任何 token」的 UX，通常會同時混淆產品語意與支援責任。 citeturn18view8turn26view6turn26view7turn28view2turn28view3turn30view1

## 給你的畢業專題的建議堆疊

如果這是我的專題，我會把交付展示範圍設定為**一套優秀的即時堆疊加上選擇性擴充性**，而不是第一天就完美支援每個供應商。最有說服力的基準是 **OpenAI-first** 或 **Gemini-first**。OpenAI 給你一個在**即時音訊**、**函式呼叫**、**串流**、**結構化輸出**與**大型上下文後續分析**之間相當乾淨的統一敘事。Gemini 則透過非常強的 **Live API**、內建**音訊轉錄**、**工具使用**和 **100 萬 token** 長上下文文字模型，提供同樣有說服力的方案。兩者都能支撐你的 UI 所需的即時「我該說什麼？」伴隨功能，以及型別化會議筆記輸出。 citeturn35view0turn35view1turn35view4turn37view0turn37view1turn11view1turn11view2turn11view5turn14view0

我的第二項建議是加入 **Anthropic**，作為非預設但高價值的供應商，用於**會議筆記生成、分析與行動項目擷取**，尤其是在你想讓使用者比較不同供應商的輸出，或重視長上下文件推理時。Anthropic 的結構化輸出與大型上下文視窗，使它非常適合通話後分析，即便它不是即時音訊擷取最乾淨的主要選擇。 citeturn7view4turn9view3turn7view5

我的第三項建議是做一個單一的**進階 OpenAI 相容轉接器**，支援 **Groq、Together、OpenRouter、Ollama 和 LM Studio**。這是你大規模滿足「使用者可以選擇自己的模型」需求的地方。OpenRouter 提供廣度與路由。Groq 提供速度。Together 提供託管開放模型多樣性加上 STT/TTS。Ollama 和 LM Studio 提供隱私優先的本機模式。這一個轉接器能把你的專題從單一供應商展示變成真正的**供應商無關系統**，同時仍然把原生即時/音訊邏輯保留在值得這麼做的供應商內。 citeturn18view7turn18view9turn18view0turn20search3turn26view6turn26view7

我**不**會做的是以 **GitHub Copilot** 作為架構核心。你絕對可以把 **Copilot SDK** 或 **Copilot CLI BYOK** 當作進階整合來實驗，尤其如果你的專題受眾是開發者，而且你想要「自帶 Copilot」模式。但 GitHub 自己的文件顯示，Copilot 仍然是**Copilot 形狀的介面**，具有預覽範圍 SDK、CLI 耦合、組織雲端 agent API，以及產品特定限制，而不是會議輔助工具最簡單的通用基礎。同樣地，我會把 **OpenAI Codex** 視為選配，而且只有在你明確想在會議功能旁加入寫程式 agent 模式時才加入。 citeturn28view2turn28view6turn34view1turn34view2turn30view2turn30view3

因此，達成強成果的最短路徑是：**針對即時會議 UX 使用原生 OpenAI 或 Gemini、把 Anthropic 作為選配分析、用一個 OpenAI 相容轉接器提供模型選擇廣度，並把本機 Ollama/LM Studio 支援作為隱私模式**。這會讓你的畢業專題兼具學術趣味與產品可信度：它展示了即時 AI 輔助、型別化行動項目擷取、供應商抽象層、自帶金鑰（BYOK），以及本機模型擴充性，同時不會強迫 GitHub Copilot 或 Codex 扮演它們原本並非主要設計來承擔的角色。 citeturn35view4turn37view0turn11view1turn7view4turn18view7turn26view6
