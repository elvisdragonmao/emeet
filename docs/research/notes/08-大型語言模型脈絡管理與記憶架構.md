# 大型語言模型脈絡管理與記憶架構 筆記

## 重點整理
- 會議助理不應把整場逐字稿全部塞進長脈絡，因為長脈絡不等於可靠記憶，而且成本和延遲會失控。
- 比較好的做法是分層記憶：最新原文、近期視窗、滾動摘要、結構化狀態、完整逐字稿、檢索索引、會後分層摘要。
- 不同功能有不同延遲需求，不能共用同一條慢管線。
- 即時字幕和「我該說什麼？」需要最低延遲；會中筆記可以幾秒更新一次；會後總結可以慢一點但要完整。
- 「我該說什麼？」最需要的是最近 1-3 分鐘原文加上目前會議狀態，不一定需要查完整歷史。
- 聊天框和會後整理才比較需要檢索完整逐字稿、主題摘要或過去會議內容。
- 結構化狀態很重要，不能只在最後輸出 JSON。topics、decisions、todos、open issues、risks 應該是會中持續更新的中繼記憶。
- 滾動摘要可以降低 token 成本，但會累積誤差，所以要保留原始逐字稿證據，必要時回查。
- 檢索不應每次都做。沒有跨段問題時，直接用近期視窗比較快也比較便宜。
- 會議檢索不能只靠向量，因為人名、日期、ticket ID、版本號、產品名這種精確字詞很多，FTS 很有用。
- SQLite FTS5 + 本地向量索引比較適合第一版桌面 App；Pinecone / Milvus 更適合後期雲端團隊版。
- 本地資料應該是權威副本，尤其會議內容敏感，又需要離線可用。
- 所有摘要、決策、todo 都應該能回指 `segment_id`，這樣使用者才能知道 AI 根據哪段話整理。
- 模型部署最務實是混合式：本地小模型或便宜快模型處理即時路徑，雲端強模型處理會後整理和複雜問答。
- 提示詞快取只適合穩定前綴，例如系統規則、使用者風格、會議目標，不適合每秒變動的逐字稿尾端。

## 對專題的影響
- 第一版不需要一開始就做複雜 RAG 平台，先把本地 SQLite、近期視窗、滾動摘要和結構化狀態做好比較實際。
- 即時建議若每次都讀整場會議，延遲會太高；應該限制在最近內容和少量狀態。
- 聊天框可以比建議按鈕慢一點，所以可以允許它觸發 FTS 或向量檢索。
- 會後筆記可以使用 map-reduce 或遞迴摘要，因為它不在即時壓力下。
- 本地優先對專題展示很加分：可以強調隱私、離線、成本低、資料可追溯。
- 模型選擇器要能分任務設定，不是整個 App 只選一個模型。例如即時建議用快模型，會後整理用強模型。
- 如果未來要接 GitHub Models / OpenAI / Gemini / Anthropic，應先做 provider abstraction，避免 UI 和資料層綁死某一家。

## 可以採用的做法
- 記憶層可以照這樣設計：
  - Tier 0：ASR 局部緩衝，給字幕用。
  - Tier 1：最近 1-3 分鐘 final transcript，給即時建議用。
  - Tier 2：rolling summary，給會中背景脈絡用。
  - Tier 3：structured state，保存 topics / decisions / todos / open issues / risks。
  - Tier 4：完整逐字稿 + SQLite FTS5 + 本地 embeddings。
  - Tier 5：topic / section / final summary，給會後整理和長距離問答用。
- `transcript_segment` 應該是事實來源，欄位包含 meeting id、speaker id、start / end time、text、is_final、topic id。
- `evidence_link` 用來把 summary、decision、todo、open issue 連回原始 segment。
- `state_item` 用來保存會中結構化狀態，例如決策、任務、風險、待釐清問題。
- 檢索路由可以採這個順序：
  - 先查 structured state。
  - 若問題是最近內容，直接用近期視窗。
  - 有人名、日期、ID、產品名時先用 FTS。
  - 語意模糊或跨很久才用向量檢索。
  - 命中後展開前後幾段當證據視窗。
- SQLite 使用 WAL，讓寫入逐字稿時 UI 仍能讀取資料。
- 如果要加密，密鑰放 Keychain，資料庫可用 SQLCipher；系統層再依賴 FileVault。
- 同步可以先做單使用者 append-only oplog，不需要一開始就上 CRDT。
- 成本控制要靠三件事：限制即時提示詞長度、只快取穩定前綴、檢索按需觸發。
- 評估要分層：
  - 延遲：字幕首字、建議首 token、完整建議完成。
  - 檢索：Recall@k、MRR、證據跨度正確率。
  - 建議：可說、貼題、得體、不中斷。
  - 摘要 / todo：完整性、忠實性、決策和任務覆蓋率。
  - 成本：每場 token、cache hit rate、embedding 數量、雲端花費。

## 風險與待確認
- 長脈絡模型雖然看起來方便，但可能在中段資訊抓得不穩，也會讓成本和延遲變高。
- 滾動摘要如果不定期回查原文，錯誤會一路傳到後續筆記和聊天。
- 向量檢索可能漏掉精確字詞，所以不能取代全文搜尋。
- 本地向量索引要處理持久化、segment 對應、embedding model 版本，否則之後很難維護。
- 如果 ASR segment 之後被修正，summary 和 state item 也要局部重算或標示過期。
- 雲端模型的資料保留、ZDR、價格和可用模型會變動，provider 設計要能替換。
- 本地模型雖然隱私好，但品質、延遲、記憶體需求要在目標 Mac 上實測。
- 如果之後要多人共同編輯筆記，單純 oplog 可能不夠，才需要研究 CRDT。
