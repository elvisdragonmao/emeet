# 模型供應商與自帶金鑰研究 筆記

## 重點整理
- 這篇最重要的結論是：使用者可以自己選模型、自己帶 API key，但 App 不能只做一個「輸入 token 就好」的假通用介面。
- 真正要抽象的不是供應商名稱，而是能力：串流、工具呼叫、結構化輸出、音訊輸入、音訊輸出、長上下文、延遲、是否能本機跑。
- 即時會議助理的核心場景是「聽到對方講話後，快速給我可以說出口的建議」，所以原生即時音訊能力很重要。
- OpenAI 和 Gemini 最適合作為第一版主要供應商，因為兩者都有比較完整的即時音訊、串流、工具和結構化輸出路徑。
- Anthropic Claude 很適合長上下文分析、會議摘要、筆記整理、行動項目抽取，但不是最乾淨的即時音訊通道。
- Groq 的價值在速度，Together 的價值在開放模型廣度，OpenRouter 的價值在路由和模型選擇。
- Ollama 和 LM Studio 比較適合當成本機 LLM 後端，支援隱私模式、離線展示或使用者自帶本機模型。
- GitHub Copilot 和 OpenAI Codex 要分開看：Copilot 是 Copilot 產品介面，不是一般第三方 App 的通用聊天 API；Codex 是 coding agent，不是會議助理預設後端。
- OpenAI 相容 API 很有用，但只能當「方便整合」的基礎，不能假設每個 OpenAI 相容端點都支援一樣的工具、音訊和結構化輸出。
- BYOK 也有不同型態：直接輸入供應商 key、輸入 OpenRouter 這種路由器 key、連本機 Ollama/LM Studio、不走 API key 的本機模式、Copilot/Codex 的特殊驗證模式。
- 不同供應商的限制會直接影響 UI，例如某模型不能 structured + streaming，就不能保證一邊串流一邊產生可驗證 JSON 筆記。
- 供應商選擇其實是產品策略：要展示即時 AI 伴隨，就先選 OpenAI/Gemini；要展示模型自由度，就加 OpenAI 相容轉接器；要展示隱私，就加本機模型。

## 對專題的影響
- 不能把「模型可自行選擇」做成設定頁上的裝飾，後面需要真的有 provider abstraction。
- 「What should I say?」應該優先走低延遲、可串流、能處理最近對話脈絡的模型。
- 「Follow-up questions」可以稍微放寬延遲，但仍要輸出短句，不適合用很重的長上下文流程。
- 會議筆記和行動項目可以走另一條較慢但更穩的模型路徑，重點是結構化輸出和可靠性。
- 如果第一版想穩，建議用一個主要即時供應商加一個可擴充模型層，不要一開始就想完整支援所有供應商。
- 本機 Ollama/LM Studio 很適合放在展示中，讓老師看到「不一定要把會議內容送雲端」。
- Copilot/Codex 可以列為進階整合或開發者情境功能，例如根據會議決議產生 issue 草稿，不應該當作會議逐字稿或回覆建議核心。
- 需要在 UI 中顯示模型能力差異，例如「此模型不支援音訊輸入」、「此模型只支援文字摘要」、「此模型可離線」。
- 使用者自帶金鑰後，資料會直接送到該供應商，App 仍要提醒資料治理與隱私差異。

## 可以採用的做法
- 第一版預設做 OpenAI-first 或 Gemini-first，先把即時音訊和會議輔助體驗做穩。
- 同時設計三個內部契約：`TranscriptionProvider`、`AssistantProvider`、`CapabilityRegistry`。
- 把 STT 和 LLM 分開，不要假設同一家供應商同時負責轉錄、建議、筆記和聊天。
- 做原生轉接器給 OpenAI、Gemini、Anthropic，因為它們的最佳能力形狀不同。
- 做一個 OpenAI-compatible adapter 給 Groq、Together、OpenRouter、Ollama、LM Studio。
- 設計 capability registry，至少記錄：streaming、tool calling、structured output、audio input、audio output、context window、local/cloud、特殊限制。
- 設定頁可以分成「雲端供應商」、「路由器」、「本機模型」、「開發者工具整合」幾類，避免混在同一個 API key 欄位。
- BYOK key 儲存在 Keychain，不寫進設定檔、不進 log、不放 prompt。
- 「What should I say?」用短上下文、短輸出、串流顯示，避免為了完整性犧牲時機。
- 「Follow-up questions」固定輸出 2 到 3 題，並可標示用途，例如釐清、推進、收束。
- 會議筆記用結構化輸出，欄位可以包含 highlights、decisions、actions、owners、due_dates、open_questions。
- 對本機模型提供降級策略：可做摘要和短建議，但若品質不足，可提示使用者切到雲端模型。

## 風險與待確認
- 各供應商 API 和模型名稱更新很快，正式實作前要重新確認最新文件與價格。
- OpenAI/Gemini 即時音訊能力強，但成本、網路延遲和資料外送都要評估。
- Anthropic 很適合摘要，但如果沒有獨立 STT 路徑，就不能單獨撐起即時語音助理。
- OpenAI 相容不代表能力相同，最怕 UI 顯示可用但實際模型不支援工具或結構化輸出。
- BYOK 會帶來支援責任：使用者 key 錯、額度不足、供應商限流、模型不支援，都要有清楚錯誤訊息。
- Copilot/Codex 的授權、資料使用條款和產品範圍不適合被簡化成一般 LLM API。
- 本機模型品質與速度會受硬體影響，必須限制上下文和輸出長度。
- 若使用 OpenRouter 這類路由器，還要確認資料實際會送到哪個上游供應商。
- 需要避免讓模型選擇功能拖垮 MVP，第一版應先支援少數高信心路徑。
