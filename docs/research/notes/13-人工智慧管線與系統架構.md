# 人工智慧管線與系統架構 筆記

## 重點整理
- 這篇的核心是：會議助理的關鍵不是單一模型，而是一條可觀測、可回滾、可降級的事件管線。
- 最佳預設是本地優先的混合式架構，不是全雲端，也不是硬做全本機。
- macOS 端應負責音訊擷取、VAD、重取樣、初步遮罩、暫定逐字稿 UI、本地快取和基本離線能力。
- 後端或雲端可負責較重的 LLM 推理、供應商路由、工具執行、同步、稽核和觀測。
- 如果主打高隱私或離線，完全本地也成立：本機 STT、小型本機 LLM、本機筆記抽取、本機儲存。
- 最大實作難點是雙音源擷取和逐字稿一致性，不是 LLM 本身。
- 麥克風和會議 app/系統音訊最好分通道處理，不要一開始就混音，這樣對話者來源、成本和準確率都比較好。
- 逐字稿必須支援暫定結果、最終結果、時間戳、信心分數、修正、段落合併和來源標籤。
- 熱路徑應優先可用：字幕和建議要快；會後摘要、完整話者分離、工具代理可以晚一點。
- 「What should I say?」、「Follow-up questions」、「AI 聊天」不應共用同一個巨大 prompt，三者 SLA 和上下文都不同。
- 筆記管線應採階層式線上摘要，不要每次都把整場會議全文丟給模型。
- 儲存應採只能附加的事件日誌，再產生衍生檢視，這樣可重算、可同步、可追蹤錯誤。
- 外部 API、Copilot、Codex、MCP 不能直接暴露給模型，必須經工具中介層、政策、使用者確認和審計。
- 離線模式應是一級功能，至少保留本地音訊、VAD、STT、字幕、簡短建議、筆記快照和本地儲存。

## 對專題的影響
- MVP 的第一優先不是聊天框，而是穩定的音訊擷取和逐字稿事件流。
- 沒有穩定逐字稿和事件模型，後面的建議、筆記、行動項目都會變成脆弱 prompt demo。
- 「What should I say?」要獨立成低延遲管線，輸出短句和語氣選項。
- 「Follow-up questions」要獨立成追問管線，輸出少量問題，最好分釐清、推進、收束。
- AI 聊天可以較慢，使用整場會議的摘要、檢索和工具，但要清楚標示來源。
- 會議筆記要每 30 到 90 秒更新一次 snapshot，會後再做高品質整理。
- 儲存格式要能留下 evidence turn ids，避免 AI 筆記無法追溯。
- 如果要串 GitHub Copilot/Codex，應定位成開發者工具 skill，例如建立 issue 草稿，不是會議大腦。
- 後端不是一開始必須很大，但若要做供應商路由、工具治理和短效 token，後端會比純客戶端安全。
- 評估不能只看模型回答好不好，還要看 WER/CER、延遲、採納率、行動項目精準度、能耗和使用者體驗。

## 可以採用的做法
- 先做本地熱路徑：麥克風擷取、系統/會議音訊擷取、VAD、STT、逐字稿合併器、浮動面板。
- 音訊來源盡量分開：local mic、remote/system audio、可能的 app source，各自保留 timestamp 和 source label。
- 內部音訊處理可用短 frame，傳輸前再聚合，並在資料中加入序號、stream id、單調時間戳。
- 若傳音訊到後端，網路穩定時可用 PCM16 方便除錯，網路變動大時評估 Opus。
- 逐字稿事件模型至少包含：segment_id、turn_id、source、speaker_hint、start/end time、text、is_final、confidence、revision。
- UI 顯示可以吃暫定逐字稿，但筆記、行動項目、搜尋索引只吃 final 或 confirmed 文字。
- 建議管線分兩段：先做輕量意圖偵測，再做建議生成。
- 「What should I say?」上下文可用最近 30 到 120 秒 final transcript，加上一小段 current hypothesis 和使用者角色。
- 「Follow-up questions」輸出固定 3 題，避免模型發散。
- 聊天框用 RAG 或摘要 state，不直接塞完整 transcript history。
- 筆記 JSON 欄位可設為 highlights、decisions、actions、owners、due_dates、open_questions、risks、evidence_turn_ids。
- 儲存採 append-only event log，筆記和 UI 是 materialized view，之後可重算。
- 背壓策略順序：先停自動建議，再降低筆記更新頻率，再停外部工具，最後才影響 STT。
- STT 失敗時先保存音訊片段和事件索引，之後補轉錄。
- 供應商層做 adapter 和 router，並記錄每個 provider/model 的能力和隱私模式。
- 工具中介層必須有 allowlist、使用者確認、tool_call_id、審計日誌和權限範圍。
- 本機儲存可用 SQLite/GRDB 或 Core Data；若要 Apple 生態同步，可考慮 CloudKit private database。
- 觀測用 OpenTelemetry 或類似概念，客戶端也要有 signpost、錯誤、延遲和 queue depth 指標。
- 開發順序建議：音訊擷取與逐字稿熱路徑，再做兩個按鈕，再做筆記，最後做聊天與外部工具。

## 風險與待確認
- 系統音訊擷取和會議 app 音訊路由會是最大不確定性，要在實際 Zoom、Meet、Teams 測。
- 即時多講者話者分離仍然困難，熱路徑先做來源分離，會後再做真正 diarization 比較務實。
- 完全本地版隱私最好，但模型打包、更新、硬體差異、效能調校都會提高複雜度。
- 混合式能力最完整，但會帶來後端成本、供應商資料治理、同步和安全管理。
- WebSocket 幀邊界不能當音訊語意邊界，必須自己處理序號和時間戳。
- 無界 queue、無限制 prompt、整場會議全文重跑，都會讓長會議越跑越慢。
- 筆記行動項目最怕幻覺負責人和到期日，要以 evidence 和人工確認為主。
- 外部工具和 MCP 的風險比純回答高，不能讓模型自動執行高風險動作。
- BYOK 和供應商路由會讓成本、限流、錯誤處理變複雜，需要清楚的 UI 狀態。
- 若最低支援 macOS 12，很多較新 Apple API 要有替代路徑或版本判斷。
- 評估資料集要包含中文、英文、混合語言、口音、重疊說話和背景噪音，不然 demo 結果太樂觀。
