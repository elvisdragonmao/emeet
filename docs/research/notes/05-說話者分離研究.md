# 說話者分離研究 筆記

## 重點整理
- 說話者分離要先分清楚兩件事：一是「現在是哪個 speaker 在講」，二是「這個 speaker 真實身份是誰」。前者比較可做，後者需要額外線索。
- 單一混音音軌通常只能穩定做到 `speaker_0`、`speaker_1` 這種工作階段內標籤，不應期待模型自己可靠猜出 Alice、Bob 這種真名。
- 如果要把 speaker label 對到真實人名，需要已知聲音參考、聲紋、會議平台參與者資訊，或每位參與者獨立音軌。
- 對我的專題來說，最重要的其實不是一開始就分出所有人，而是先分出「我」和「其他人」。
- macOS 上如果能把麥克風音訊和會議 App / 系統輸出音訊拆成兩條，就可以用音源直接判斷「我 vs 其他人」，比在單一混音裡做聲學推斷穩很多。
- ScreenCaptureKit 和 Core Audio tap 都是值得研究的路線：前者可以抓螢幕與音訊，後者可以針對特定程序或程序群組抓輸出音訊。
- 即時回應建議不能等說話者分離全部算完才開始，因為說話者標籤通常比文字慢、也更容易回補修正。
- 比較合理的架構是雙速路徑：快速 ASR 先產生暫定文字讓 AI 建議可以動起來，較慢的說話者分離在背景修正逐字稿和筆記。
- 重疊語音是主要失敗來源。兩個人同時講話時，不只 speaker label 會錯，STT 也可能把句子和說話者對錯。
- OpenAI 的具說話者分離轉錄適合當雲端品質比較或後處理，但目前不適合把「即時 speaker label」當產品核心依賴。
- pyannote.audio 適合當研究基線或伺服器端補正工具，優點是研究成熟、可本機跑；缺點是 Python / PyTorch 和 Swift macOS app 整合成本較高。
- WhisperKit + SpeakerKit 是比較貼近 macOS / Apple Silicon 的本機路線，尤其適合畢業專題先做可展示原型。
- Zoom RTMS 如果能接到，說話者歸屬會容易很多，因為平台層可以提供參與者身份或多路音訊，不必全靠模型猜。
- Teams 的平台級原始媒體整合門檻比較高，對第一版 macOS 助理不太適合當主線。
- 評估時不能只看 DER，還要看說話者切換時間、重疊語音、逐字稿的詞級歸屬，以及錯誤是否真的影響「我該說什麼？」和行動項目。

## 對專題的影響
- MVP 不應把「完美多人說話者命名」列為第一版必做，否則會卡在難度最高、Demo 風險最大的部分。
- 第一版應該把目標縮成：能穩定知道目前是「我」在講，還是「會議中的其他人」在講。
- UI 上要明確標示 speaker label 可能是暫定的，避免使用者誤以為 AI 已經完全知道每個人身份。
- 即時建議按鈕應主要依賴最近穩定文字、說話輪次、問題偵測，而不是依賴最終 speaker diarization。
- 會議筆記與行動項目可以等背景分離結果回補後再修正，這樣會比即時畫面更可靠。
- 如果使用者要顯示人名，最好讓他手動對應 speaker，或從會議平台 metadata / 參與者清單取得，不要讓模型硬猜。
- 隱私面要早點決定：本機 SpeakerKit / pyannote 比較安全，OpenAI / pyannoteAI 雲端 API 比較快做但音訊要送出去。
- Demo 場景最好先用耳機會議和兩到三人對話，避免一開始就測多人搶話、遠場、喇叭回灌這種高難度情境。

## 可以採用的做法
- 第一版技術組合：WhisperKit 做本機串流 ASR，ScreenCaptureKit / Core Audio tap 拆麥克風與會議音訊，SpeakerKit 做背景說話者分離補正。
- 把資料流拆成兩條：
  - 即時路徑：音訊擷取 -> ASR -> 穩定文字 -> 問題 / 輪次偵測 -> 回應建議。
  - 品質路徑：音訊緩衝 -> 說話者分離 -> speaker 對帳 -> 最終逐字稿 -> 筆記 / 行動項目。
- 設計 speaker 狀態時至少分成 `self`、`other`、`unknown`，先不要急著做每個人的姓名。
- 每段逐字稿保留 speaker label、來源音軌、時間戳、是否為暫定、是否被背景分離修正過。
- 對重疊語音或 speaker 不確定時，UI 和建議引擎都採保守策略，例如不要主動產生太肯定的答句。
- 用 pyannote.audio 當離線比較基線，檢查 SpeakerKit 或其他本機方法在同一批測試音檔上的差異。
- 如果要支援 Zoom，可以把 RTMS 當進階整合路線；但第一版仍先做一般 macOS 音訊擷取，產品彈性比較高。
- 測試集要包含：兩人耳機會議、三人會議、喇叭外放、有打斷、中文 / 中英混合、背景噪音。
- 指標可以分兩層：研究指標看 DER / JER / speaker switch；產品指標看建議是否用錯視角、行動項目 owner 是否錯、使用者修正次數。

## 風險與待確認
- ScreenCaptureKit 與 Core Audio tap 的權限、格式、取樣率、聲道處理要先做小 POC，不然音訊路由會變成主要風險。
- 麥克風可能收到會議喇叭回音，導致「我 vs 其他人」誤判；Demo 最好要求戴耳機。
- 不同會議 App 的降噪、回音消除、voice isolation 會改變音訊特徵，不能假設抓到的是原始聲音。
- SpeakerKit OSS 是否能支援足夠即時的多人分離，需要實測；公開資料比較偏本機離線或 Pro SDK 能力。
- OpenAI diarization 的即時能力邊界要保守看待，不能把尚不穩定或文件不明確的能力當硬需求。
- 單一混音在多人搶話、遠場、相似音色、短句快速輪替時會明顯變差，這要在報告中承認。
- 如果要做聲紋或已知說話者註冊，會牽涉更高隱私敏感度，需要同意、儲存方式和刪除機制。
- BlackHole 這類虛擬音訊裝置可用來 POC，但散佈到正式產品時要確認授權與安裝 UX。
