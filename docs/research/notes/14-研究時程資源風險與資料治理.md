# 研究時程資源風險與資料治理 筆記

## 重點整理
- 這份資料提醒我，會議助理不能只當成模型 demo，還要把研究設計、資料治理、使用者同意和評估方法一起規劃。
- macOS App 會碰到兩種關鍵權限：麥克風權限，以及如果要抓會議或系統音訊，可能需要螢幕錄製或系統音訊擷取相關權限。
- 權限流程不只是技術問題，會直接影響第一次使用的信任感和展示成功率。
- 研究上不能只看 WER、ROUGE、BERTScore 這類自動指標，因為會議筆記更在意事實是否正確、行動項目是否有根據、負責人和期限有沒有亂猜。
- 主動式 AI 建議有風險：太常跳出來會打斷會議，使用者可能覺得聰明但很吵。
- 模型供應商會更新模型，或自動選模造成結果漂移，所以正式測試時要記錄模型 ID、提示詞版本和輸入資料版本。
- 公共會議資料集很難代表台灣雙語、混語、口音、企業內部會議和敏感會議，所以不能完全依賴公開資料。
- 資料治理的核心是分層保存：原始音訊、去識別化逐字稿、摘要、行動項目、系統遙測要分開看。

## 對專題的影響
- 我的專題如果只展示「可以即時轉文字」，說服力不夠；要能說清楚資料怎麼存、誰能刪、什麼時候上傳、什麼時候只留本機。
- 會議前的告知和會議中的可見狀態很重要，否則即使功能可用，也會讓人覺得被偷錄或不透明。
- 即時建議功能應該先做成使用者按按鈕觸發，而不是 AI 一直自動插話。
- 低信心逐字稿會污染後面的建議與筆記，所以 UI 要能呈現不確定狀態，必要時只顯示字幕、不產生建議。
- 一學期版本應該把完整研究時程壓縮成可展示 MVP，但報告中仍要交代完整產品需要更長的試點、標註和人評。
- 如果支援 BYOK 或多模型，研究結果就會受平台差異影響，不能把不同模型跑出來的結果混在一起比較。

## 可以採用的做法
- 開始會議前顯示簡短告知：會轉錄什麼、是否送到雲端、資料保存多久、使用者可以如何刪除。
- 會議中保持明顯狀態，例如錄音中、轉錄中、雲端處理中、AI 建議已啟用。
- 會議後提供下載、刪除、清除 AI 產物和撤回後續分析的操作。
- 預設原始音訊短期保存，甚至 MVP 可以不保存原始音訊，只保存逐字稿與摘要。
- 把原始內容、摘要、行動項目、聊天紀錄和匿名化遙測分開存，不要混成一個不可分辨的資料堆。
- 評估時至少分三層：工程指標、人工品質檢查、真實或半真實會議試用回饋。
- 人工評估重點放在事實正確、行動項目 precision/recall、是否過度承諾、建議是否自然可用。
- 測試時凍結模型與提示詞版本，所有輸出都記錄 provider、model、prompt version、schema version。
- 準備一小套自建雙語會議腳本，用來補公開資料無法代表本地場景的問題。
- 設計安靜模式、節流規則和手動觸發按鈕，降低 AI 打斷會議的機率。

## 風險與待確認
- 不同地區對錄音同意的規則不同，正式產品一定要再查法規；畢業專題也至少要有明確告知。
- ScreenCaptureKit 或系統音訊擷取的權限流程可能需要重啟 App，展示前要先演練。
- 自動評估器目前只能當輔助，不能取代人工判斷。
- 混語、口音、遠端會議音質會讓 ASR 品質下降，後面所有 AI 功能都會被影響。
- 使用者可能因隱私顧慮不願意提供真實會議資料，研究樣本會偏向低敏感場景。
- 模型供應商更新、價格變動、API 政策調整都會影響結果，需要在報告中把時間點寫清楚。
- 如果未來要支援 GitHub Copilot、Codex 或其他模型介面，要先確認它們是不是適合當 App 的後端推論 API，而不是只因為名字熟悉就接入。
