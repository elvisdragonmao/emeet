# 提示詞工程與結構化輸出策略 筆記

## 重點整理
- 會議助理不應該靠一個萬用提示詞處理所有事情；逐字稿、即時話術、追問、筆記、聊天都應該分成不同任務。
- 最穩的設計是任務分流、JSON Schema、證據綁定、狀態機和回歸測試，而不是期待模型每次自由輸出都剛好可用。
- UI 要讓模型輸出資料，不要讓模型直接決定畫面格式；格式控制應該在客戶端。
- 逐字稿、投影片、附件和聊天內容都要視為不可信資料，不能放進 system/developer 層當規則。
- 長上下文不是萬能，模型容易漏掉中段資訊；每次推理應用「最近窗口 + 壓縮狀態 + 找到的證據片段」。
- 建議和筆記都要能回鏈到逐字稿片段，否則很難檢查幻覺。
- 「不知道」「未明示」「owner 為 null」「due date 為 null」都應該是合法輸出，不要逼模型亂猜。
- 會議筆記比話術建議需要更高忠實度，可以用草稿到驗證的二階段流程；即時按鈕則要優先低延遲。

## 對專題的影響
- What should I say 和 Follow-up questions 應該是兩個獨立 prompt，各自有固定 schema，不要共用聊天 prompt。
- 即時建議要短、保守、可直接念出來，並避免替使用者承諾日期、預算、法務核准或責任歸屬。
- 追問問題要針對資訊缺口，不是問空泛社交問題；優先順序是阻塞決策、責任分配、時程風險。
- 會議筆記應輸出決策、行動項目、風險、未決問題和 unsupported claims，讓 UI 可以清楚呈現不確定資訊。
- 多模型支援要建立在共同資料契約上，不能每換一家供應商就改 UI parser。
- Codex 比較適合幫我做開發流程，例如產生測試、分析逐字稿資料、跑回歸工具；不適合當一般會議話術模型預設路由。

## 可以採用的做法
- 提示詞固定分層：核心系統規則、任務角色、輸出 schema、少樣本範例、會議狀態、證據片段、最新逐字稿、使用者請求。
- 靜態規則和 schema 放在前面，動態逐字稿放後面，這同時有利於 prompt caching 和降低 prompt injection 風險。
- 建立 `meeting_state`，內容包含目前議題、會議階段、使用者角色、已確認決策、承諾事項、未決問題、風險、專有名詞和最近被問到的問題。
- SuggestedReply 可以包含 `reply_text`、`tone`、`intent`、`rationale`、`confidence`、`uncertainty_note`、`do_not_say`、`evidence`。
- Follow-up questions 可以包含問題、目的、優先級、問題類型和 evidence。
- MeetingNotes 可以包含 title、executive summary、decisions、action_items、risks、open_questions、unsupported_claims。
- 所有 schema 都應版本化，例如 `suggested_reply_v1`、`meeting_notes_v3`，方便日後遷移和回歸測試。
- schema 盡量扁平，不要做太深的自由樹；欄位需要可空時明確允許 null。
- 模型路由依任務選：ASR 用低延遲語音模型，即時按鈕用小型快速文字模型，會議筆記用較高準確度模型，聊天用檢索加證據回答。
- 每次模型輸出先過 JSON validator，再渲染到 UI；解析失敗要能重試或顯示安全 fallback。
- 建立四組測試資料：格式回歸、忠實度回歸、按鈕行為回歸、安全/提示詞注入回歸。

## 風險與待確認
- 不同供應商雖然都說支援 JSON schema，但支援細節、快取、延遲和決定性能力不完全一樣。
- seed 或固定溫度不能保證格式穩定，真正的穩定還是要靠 schema、validator 和測試。
- ASR 品質會直接限制後面所有 AI 功能；人名、專案代號、混語和說話者分離尤其需要測。
- 行動項目抽取很容易誤判，owner 和期限沒有明講就要保持 null 或 candidate。
- 提示詞注入要用測試集固定檢查，例如逐字稿裡有人說「忽略前面規則」時，模型不能照做。
- 長會議會造成 token、延遲和成本壓力，所以狀態歸約器比超長 prompt 更重要。
- 模型更新會造成輸出風格或格式變化，正式展示前要凍結模型版本並重跑回歸。
- 若未來加入投影片、文件或 email 當補充資料，證據來源要分清楚是 transcript segment、slide 還是 document excerpt。
