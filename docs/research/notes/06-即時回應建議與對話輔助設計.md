# 即時回應建議與對話輔助設計 筆記

## 重點整理
- 這個功能不能做成「任何時候都叫 LLM 生一句話」，應該先判斷現在是否值得介入，再判斷要給哪一種建議。
- 會議助理比較適合鏈式管線，不適合一開始就全部交給端到端語音代理。原因是我需要逐字稿、筆記、行動項目、聊天證據和安全規則。
- 管線可以拆成：音訊擷取、串流 ASR、逐字稿狀態、問題偵測、會議狀態分類、提示詞建構、模型路由、建議重排序、UI 呈現。
- 建議產生前應該有門控器，至少看五個訊號：發話是否結束、ASR 是否穩定、對方是否在問問題、目前會議狀態、是否有承諾風險。
- 對話狀態不要只分「問題 / 非問題」，還應該分出異議、需求描述、決策點、卡住、閒聊等情境。
- 「我該說什麼？」和「追問問題」其實是兩個不同任務：前者偏可直接講出口的短答，後者偏釐清需求或推進會議。
- 建議格式可以分成四種：單句、詳細版、追問問題、風險提醒。UI 預設只露出短句，需要時再展開。
- 生成內容要像人真的會在會議裡說的話，不要像 email 或正式報告。
- 最重要的安全規則是：AI 只能建議，不能替使用者自動發言，也不能自動對外承諾 deadline、預算或保證。
- 高風險語意包含「一定可以」、「保證」、「下週一定交」、「沒問題我們會做」這類承諾句，應該被降分或改寫。
- 模型供應商要做抽象層。OpenAI / Gemini 這類即時或推理 API 可當主要 runtime；GitHub Models 適合做模型選擇和比較；Copilot / Codex 更適合開發或研究 adapter，不適合直接當會議執行階段核心。
- macOS 音訊來源應分成麥克風和系統 / App 音訊，這樣對即時對話輔助比較穩。
- UX 不應一直跳大段文字，而是用低干擾的 chips、popover、側邊筆記和按鈕式互動。

## 對專題的影響
- 我的 Demo 重點可以放在「AI 何時該幫忙」和「建議是否自然安全」，而不是只展示 LLM 會生句子。
- 第一版應該做兩顆清楚的按鈕：`我該說什麼？` 和 `追問問題`，再加上簡短建議 chips。
- 即時建議要吃穩定逐字稿，不要吃還在大幅改寫的局部 ASR，不然建議會一直跟著抖。
- 如果分類器不夠準，寧可讓使用者按按鈕觸發，也不要讓 AI 自動浮現太多錯誤建議。
- 產品定位應和一般 note taker 拉開：不是只做會後摘要，而是主打會中說話輔助 + 筆記 + 行動項目。
- 模型選擇 UI 要讓使用者可以換 provider，但內部仍要統一輸出格式，否則後續 UI 和評估會很難做。
- 安全防護欄要在提示詞、重排序器、UI 三層都做，不能只靠一句 prompt。

## 可以採用的做法
- 建立一個 `SuggestionEngine`，輸入最近 30-60 秒穩定逐字稿、目前 speaker 狀態、會議狀態、使用者風格，輸出 1-3 個短建議。
- 建立一個小型門控器，規則先不用太複雜：
  - `turn_complete_confidence` 高才自動建議。
  - `asr_stability` 低就不主動建議。
  - `question_probability` 高時優先顯示「我該說什麼？」。
  - `meeting_state` 是異議、卡住、決策點時優先顯示「追問問題」。
  - `commitment_risk` 高時只給保守說法。
- 分類器 schema 可以包含：`is_question`、`question_type`、`meeting_state`、`commitment_risk`、`suggested_output_format`。
- 提示詞固定分段：角色目標、最近會議內容、使用者風格、生成規則、承諾防護、輸出格式、短範例。
- 輸出格式先用 JSON，例如 `suggestions`、`type`、`risk_level`、`reason_short`，方便 UI 穩定接。
- 風格預設用使用者看得懂的選項，不直接暴露 temperature：
  - 自然口語：一般討論。
  - 短句：高節奏會議。
  - 正式：客戶 / 面試 / 報告。
  - 保守：牽涉承諾、期限、成本。
- 「我該說什麼？」的輸出應限制很短，每句最多一到兩個子句。
- 「追問問題」每句只問一件事，避免一次塞多個問題。
- 高風險場景的預設句型可以是：「我先確認範圍和資源，再回你一個比較準的時間。」
- UI 互動可以設計成：使用者點 chip 後可複製、編輯、釘選；系統記錄接受、忽略、編輯距離，當成之後評估資料。
- 評估時請同學人工評分：是否貼題、是否可說出口、是否自然、是否避免過度承諾。

## 風險與待確認
- 問題偵測若只看問號或疑問詞會不夠，中文會議常有陳述式問題，可能需要語氣、停頓和上下文。
- ASR 幻覺或局部文字抖動會讓建議跑偏，所以 VAD、穩定文字和 suppress 策略要先做好。
- AI 建議太積極會打斷使用者，應該用保守門控和按鈕式觸發降低干擾。
- 生成句太長、太正式、太像客服話術，會讓使用者不想採用，這需要用人工評估修。
- Copilot / Codex 若接進來，要注意它們本來是 coding agent，可能有本機檔案和 shell 權限，不適合直接放在未隔離的會議 runtime。
- 不同模型的延遲和輸出風格差異很大，模型路由器要能針對即時建議和會後整理分開設定。
- 隱私告知不能只放設定頁；使用者必須知道目前 App 正在聽麥克風、會議音訊，或是否有送雲端。
- 需要確認中文、英文、中英混合的建議品質，不能只用英文資料集推論。
