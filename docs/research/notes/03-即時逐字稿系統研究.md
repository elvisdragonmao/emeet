# 即時逐字稿系統研究 筆記

## 重點整理
- 最穩的逐字稿架構不是單押雲端或單押本機，而是本機優先、雲端增強、可離線降級。
- 本機路線的主要候選是 Apple SpeechAnalyzer / SpeechTranscriber 和 WhisperKit；它們都比較適合 macOS 原生 App。
- OpenAI Realtime 的優勢是串流事件、雲端整合和後續 AI 功能，但網路、成本、資料送雲端都是要考慮的限制。
- 原始 Whisper 很強，但不是天生為低延遲串流 UI 設計；WhisperKit 比較符合 Apple Silicon 和 Swift App 的需求。
- faster-whisper 在伺服器或 Python 工具鏈很成熟，但 macOS 上通常不是 Apple Silicon 最自然的原生路線。
- 即時字幕和最終高品質稿應該分成兩條管線：即時路徑追求低延遲，會後/定稿路徑追求準確、標點、說話者標記和整理。
- zh-TW、台灣口音、中文英文混講是最大準確率風險，不能只看英文 benchmark。

## 對專題的影響
- MVP 應該先讓字幕穩定跑起來，再把 LLM 回覆建議接上去。
- 如果即時字幕完全依賴雲端，弱網路或 API 延遲會讓整個產品失效。
- 本機 STT 可以降低長期成本，也比較容易主打隱私，但要處理模型下載、硬體效能、電量和散熱。
- 雲端 STT 可作為加強或會後清理，不應一開始就成為唯一真相來源。
- 逐字稿資料模型不能是一條不斷 append 的字串，因為部分結果會被修正，必須支援 partial / final / revision。
- 回覆建議和會議筆記應該主要吃已定稿或高穩定度內容，避免建議跟著錯誤的部分字幕一直改。

## 可以採用的做法
- 架構上分三層：音訊擷取與前處理、本機逐字稿、雲端增強。
- 優先實作一個本機後端，例如 WhisperKit；如果鎖定較新 macOS，再評估 Apple SpeechTranscriber。
- OpenAI 可以先接在會後定稿、摘要、說話者標記或高品質清理，不一定一開始就接即時 Realtime。
- 音訊格式轉換集中在擷取層做，不要讓每個 STT 後端自己處理；雲端常用 16 kHz 或 24 kHz 單聲道 PCM。
- 逐字稿片段至少要有 `segmentId`、來源、狀態、開始/結束時間、文字、revision、provider metadata。
- UI 上把可變字幕和已定稿字幕分開顯示，例如不穩定尾巴用較淡樣式，最後結果到來後再提交。
- 路由策略可以簡化成：隱私模式或弱網路走本機；網路好且使用者同意時，雲端做平行增強或會後清理。
- 評估資料要包含英文、台灣華語、中文英文混講、噪音、遠講、多人會議和長會議。

## 風險與待確認
- Apple SpeechTranscriber 的語言支援與實際 zh-TW 準確率需要自己測，不要只依賴官方名稱。
- OpenAI 語音模型公開資訊不一定有 zh-TW / zh+en 的細分數字，正式選型前要做自己的小型評估集。
- 如果用 OpenAI Realtime，成本大約會按會議分鐘累積；學生專題可接受，但正式產品要估算大量使用時的成本。
- 雲端 API 預設資料政策、濫用監測保存、Zero Data Retention、DPA 等都要在隱私設計中說清楚。
- 本機模型會增加下載與初始化時間，也可能造成電量和散熱問題，需要用 Instruments 或 powermetrics 實測。
- 說話者分離不要強行做成即時保證；比較穩的是即時先標「本機/遠端」或暫時 speaker，會後再校正。
- 測試不能只看 WER/CER，還要量首次部分結果時間、發話結束到 final 的延遲、字幕修訂次數、建議生成延遲和長會議穩定性。
