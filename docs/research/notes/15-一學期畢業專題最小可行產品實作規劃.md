# 一學期畢業專題最小可行產品實作規劃 筆記

## 重點整理
- 一學期內做 macOS 會議助理是可行的，但前提是 MVP 範圍要砍得很清楚。
- 最穩的方向是「麥克風優先」：先確保本機麥克風擷取、即時逐字稿、AI 面板、建議按鈕、增量筆記和 Markdown 匯出能跑完。
- 系統音訊或會議 App 音訊擷取是最大平台風險，不能假設一定順利，前兩週就要做技術探勘。
- 技術堆疊建議用 Swift + SwiftUI，音訊用 AVAudioEngine；需要進階視窗、選單或權限細節時再橋接 AppKit。
- 會議音訊擷取可以研究 Core Audio taps 或 ScreenCaptureKit，但兩者都和 macOS 版本、權限、目標 App 行為有關。
- STT 第一版建議用雲端串流服務，因為本地 WhisperKit 或 Apple SpeechAnalyzer 雖然有隱私優勢，但會多出模型封裝、效能基準和相容性工作。
- LLM 層可以先用一個穩定供應商完成：聊天、What should I say、Follow-up questions、每 30 秒筆記更新。
- 說話者分離、向量搜尋、多供應商 UI、Notion/Google Docs 匯出、浮動覆蓋視窗都不適合放進第一版主線。
- 成本上通常 STT 會比文字生成更貴；真正要省成本，重點不是一直換便宜模型，而是避免每 30 秒重送整場逐字稿。

## 對專題的影響
- 我的展示要有一條「一定能成功」的路徑：就算抓不到系統音訊，也能靠麥克風模式完成端到端流程。
- 右側 AI 面板和兩個按鈕很適合展示，因為可以直接看出會議助理和普通逐字稿工具的差別。
- 30 秒增量筆記是關鍵功能，但必須用「上一版狀態 + 新逐字稿差量」更新，不能每次重新摘要全文。
- API key 處理要保守：畢業專題可讓使用者自己輸入 key，但要放 Keychain，不要放 SQLite 或設定檔純文字。
- GitHub Models 可以當未來模型供應商抽象層的方向；Copilot 或 Codex 比較像開發工具或 coding agent，不應該直接當會議話術預設模型。
- 報告可以把「延期功能」寫清楚，表示有做技術判斷，而不是功能沒做完。

## 可以採用的做法
- MVP 功能切成：開始/停止會議、麥克風擷取、即時逐字稿、AI 聊天、What should I say、Follow-up questions、增量筆記、Markdown 匯出、本地 SQLite。
- 第 1 週完成 SwiftUI 外殼、主視窗、逐字稿區、右側 AI 面板和基本狀態模型。
- 第 2 週專門驗證音訊路徑：麥克風一定要成功，系統音訊只要得到明確可行或不可行結論。
- 第 3 到 5 週完成麥克風管線、ring buffer、STT 串流轉接器、partial/final 逐字稿 UI。
- 第 6 週先把 SQLite 存取做好，確保 App 重啟後會議資料還在。
- 第 7 到 10 週做 AI 功能：聊天框、建議按鈕、追問按鈕、30 秒筆記狀態更新。
- 第 11 週做 Markdown 匯出，內容包含摘要、決策、行動項目和逐字稿。
- 第 12 週處理系統音訊強化；如果不穩，就把它定位成延伸功能，主展示回到麥克風模式。
- 第 13 到 14 週做錯誤狀態、權限文案、延遲調整、展示腳本和備用錄影。
- 驗收目標可以設定為：1 秒內出現暫定逐字稿、停頓後 2 秒內 final、按鈕建議 2 秒內回來、筆記刷新 5 秒內完成、60 分鐘不 crash。

## 風險與待確認
- macOS 系統音訊擷取在 Zoom、Teams、Google Meet、Safari/Chrome 上的行為要實測，不能只看 API 文件。
- 如果每次筆記都送完整逐字稿，延遲和 token 成本會隨會議長度惡化。
- AI 建議可能產生不該說的承諾，所以輸出要短、保守、附根據，而且只讓使用者手動採用。
- 雲端 STT 需要網路，展示時要有離線或錄影備案。
- API key 存在桌面 App 仍有風險，正式產品應改成後端代理或臨時權杖。
- SQLite 預設不加密，若逐字稿包含敏感內容，要在報告中交代 FileVault、Keychain、SQLCipher 或資料刪除策略。
- 一個人做完整 MVP 會很緊，兩人分工較合理：一人處理 macOS/audio/UI，一人處理 AI/API/data layer。
