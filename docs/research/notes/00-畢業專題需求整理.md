# 畢業專題需求整理 筆記

## 重點整理
- 這個專題要做的是一個 macOS 會議輔助工具，不只是錄音或會議後摘要。
- 核心功能可以拆成四條線：即時逐字稿、即時回應建議、會議筆記/下一步行動、會中可問 AI 的聊天框。
- 使用者在會議中需要的是「現在可以怎麼回」和「接下來要追問什麼」，所以互動速度比漂亮的會後報告更重要。
- 介面上應該有幾個很直接的操作，例如「What should I say?」和「Follow-up questions」，讓使用者不用打長 prompt。
- 模型不能被單一供應商綁死，至少要預留使用者自帶 API key、切換模型、切換供應商的設計。
- 這個產品會處理麥克風、系統音訊、逐字稿和外部 API，因此隱私提示與權限設計會是專題的一部分，不是最後才補的東西。

## 對專題的影響
- MVP 不能只展示「我可以轉錄」，因為逐字稿本身已經是基本功能。
- 真正要展示的差異是：系統能根據目前對話內容，即時幫使用者產生可用的回覆、追問和行動項目。
- macOS App 的技術重點會落在音訊擷取、串流 STT、LLM 上下文整理、即時 UI 狀態更新。
- 產品定位要避免太寬，否則會變成什麼都做一點、但沒有一個場景真的做深。
- 如果一開始就把模型供應商抽象出來，後續接 OpenAI、Codex、GitHub Copilot 或其他 API 會比較容易。

## 可以採用的做法
- 第一版先做一個清楚的會議流程：開始擷取音訊、顯示即時逐字稿、按鈕產生回覆建議、會後輸出重點和行動項。
- UI 可以先用浮動視窗或側邊面板，讓使用者在 Zoom、Meet、Teams 等會議中也能看到輔助內容。
- 「What should I say?」要吃最近 1 到 3 分鐘的已定稿逐字稿、目前問題、使用者角色和會議目標。
- 「Follow-up questions」要偏向找出未確認資訊、風險、對方需求、下一步。
- 聊天框可以支援像「剛剛對方最在意什麼？」、「幫我整理目前待辦」這類會中查詢。
- 模型設定頁至少要有供應商、模型名稱、API key、用途分配，例如逐字稿、摘要、回覆建議分開選。

## 風險與待確認
- 要確認最低支援的 macOS 版本，因為系統音訊擷取能力會直接受版本限制。
- 要確認第一版的目標場景，建議先鎖定高壓外部會議或銷售/客戶通話，不要一開始就說適用所有會議。
- 要確認是否會上架 App Store；如果會，就要更嚴格處理錄音告知、權限、資料刪除與隱私說明。
- 要確認自帶 API 的實際可行性，尤其 GitHub Copilot/Codex 是否提供適合這類即時聊天/推理的 API 形式。
- 要避免做成「隱密錄音」或「偷偷輔助面試」的感覺，這會帶來倫理和合規風險。
