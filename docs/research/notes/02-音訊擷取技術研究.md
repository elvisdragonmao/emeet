# 音訊擷取技術研究 筆記

## 重點整理
- macOS 會議助理不能只靠麥克風，因為麥克風主要收自己的聲音，遠端參與者通常是從系統輸出音訊出來。
- 實際可用的音訊來源有四種：麥克風、系統/會議輸出音訊、虛擬音訊裝置、會議平台 SDK 或 WebRTC 原始媒體流。
- 麥克風擷取最標準的方式是 `AVAudioEngine` / AVFoundation，這條路穩、延遲低、App Store 也比較容易說明。
- 系統音訊在 Ventura/Sonoma 上可以優先研究 `ScreenCaptureKit`，但要記得音訊能力是 macOS 13 之後才比較完整。
- Big Sur / Monterey 如果要抓遠端聲音，比較務實的是 BlackHole 這類虛擬音訊裝置，把會議軟體輸出導回 App。
- 如果要逐參與者、逐音軌、比較乾淨的資料，就不能只靠 OS 混音擷取，要走 Zoom SDK、Teams Real-time Media、Meet Media API 或自己控制 WebRTC。
- Apple 新的 Core Audio taps 是未來方向，但不適合倒推成 Big Sur 到 Sonoma 的通用方案。

## 對專題的影響
- 第一版應該先驗證麥克風擷取，不要一開始就卡在系統音訊、驅動或逐應用程式擷取。
- 遠端聲音能不能抓到，會直接決定逐字稿是否真的能用於線上會議。
- 如果最低支援 macOS 13 以上，技術路線會簡單很多；如果要支援 Big Sur / Monterey，就一定要有虛擬音訊裝置回退方案。
- OS 層擷取拿到的多半是混音後聲音，對說話者分離和誰說了什麼會有天然限制。
- 權限流程會影響產品體驗：麥克風權限、Screen Recording 權限、可見錄製狀態都要被設計進 UI。
- 自製音訊驅動不是不能做，但對畢業專題來說成本太高，容易把主題從會議助理變成音訊基礎設施。

## 可以採用的做法
- PoC 第一階段：用 `AVAudioEngine.inputNode.installTap` 擷取麥克風，顯示音量或波形，錄 10 秒音訊到檔案。
- PoC 第二階段：在 macOS 13+ 加入 `ScreenCaptureKit` 的音訊通道，讓 App 同時看到麥克風和系統音訊兩路 RMS。
- 初期不要急著混成單一音軌，麥克風和系統音訊可以先分開儲存，避免時間戳、漂移和回音對齊問題變複雜。
- 舊版 macOS 回退：讓使用者把 Zoom/Teams/Meet/Discord/瀏覽器的輸出切到 BlackHole，再由 App 讀取 BlackHole 輸入。
- 音訊進 ASR 前先統一格式，例如保留本機高品質緩衝，再轉成 16 kHz 或 24 kHz 單聲道 PCM。
- 產品內要有清楚的權限前置說明：為什麼要麥克風、為什麼要螢幕擷取權限、什麼時候會啟動、怎麼停止。

## 風險與待確認
- 要先決定最低支援版本；如果包含 Monterey，不能假設 `ScreenCaptureKit` 一定能抓音訊。
- `ScreenCaptureKit` 會碰到 Screen Recording 權限，使用者授權後可能還要重啟 App，這要反映在 UX。
- 虛擬音訊裝置的工程很簡單，但使用者設定容易錯，支援成本高。
- BlackHole 是 GPL-3.0，若只是要求使用者自行安裝還好；如果要整合、重包或改作商業散布，就要確認授權。
- Loopback 是付費工具，不適合當所有使用者都必須安裝的依賴。
- App Store 審查會在意錄音告知、明確同意、持續可見的錄製狀態、資料用途和刪除方式。
- OS 混音擷取不能保證逐參與者分離；如果專題展示要標示講者，可能要先做粗略 A/B 或「本機/遠端」層級，不要承諾每個人都能準確分開。
