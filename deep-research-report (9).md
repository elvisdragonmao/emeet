# Model Provider and BYOK Research for a macOS Meeting Assistant

## Executive answer

For your capstone, **yes, users can absolutely be allowed to choose their own model and use their own API key** if you design the app around a capability-aware provider abstraction instead of hard-coding one vendor. That is straightforward for **OpenAI, Anthropic, Google Gemini, Groq, Together, OpenRouter, Ollama, and LM Studio**. The main engineering challenge is not “model selection” itself; it is that providers differ materially in **real-time audio support, tool-calling semantics, structured output guarantees, context size, and latency paths**. For a meeting assistant with **live transcript + “What should I say?” + follow-up questions + meeting notes + action items**, the strongest first-class hosted options are **OpenAI** and **Gemini**, because both document **live or low-latency audio paths** in addition to text tools and structured output features. **Anthropic** is strong for long-context analysis, notes, and tool-based reasoning, but in the official docs reviewed here it does **not** present a first-class live audio input path comparable to OpenAI Realtime or Gemini Live. **Groq, Together, and OpenRouter** are valuable as optional lanes for speed, open-model breadth, or routing, but they should not be the lowest-common-denominator contract that dictates your entire system. **Ollama and LM Studio** are viable local BYOK-style backends for privacy/offline demos, but they are best treated as **local inference targets**, not as your whole meeting stack. **GitHub Copilot is the largest boundary case**: GitHub now documents BYOK for Copilot SDK/CLI and enterprise Copilot surfaces, but those documents describe **Copilot products, SDKs, and agent workflows**, not a plain universal consumer chat API for arbitrary third-party apps. **OpenAI Codex is a different category from GitHub Copilot**: Codex-branded tools and models are real and some have API access, but they are optimized for coding, not meeting assistance. citeturn35view1turn35view4turn37view0turn37view1turn11view1turn11view2turn11view4turn7view4turn7view5turn18view7turn18view8turn26view6turn28view2turn28view3turn30view2turn30view3

A practical conclusion follows from that: if the app’s **headline demo** is “AI listens to a meeting and suggests what I should say next,” your default architecture should be **audio-first with a native realtime provider**, then layer notes and action-item extraction on top with **structured output**. If the app’s headline demo is instead “users can plug in any provider,” then you should still keep a **two-tier design**: native adapters for providers with unique realtime/audio behavior, and a generic OpenAI-compatible adapter for the rest. citeturn35view4turn37view1turn11view1turn18view6turn18view7turn26view0turn26view7

## Direct provider APIs

**OpenAI API** is the most complete single-vendor fit for your use case. OpenAI’s current docs cover **function calling**, **streaming over SSE**, a persistent **WebSocket mode** for lower-latency long-running tool workflows, **structured model outputs** with JSON Schema, and an **audio/speech stack** that spans request-based speech-to-text, streaming transcription, text-to-speech, and low-latency speech-to-speech sessions. OpenAI’s current model docs also expose large-context models: the official models overview lists **GPT-5.5** and **GPT-5.4** with **1M-token context windows**, and the GPT-4.1 family is also documented with **1M-token context** and low-latency non-reasoning behavior. For a meeting assistant, this makes OpenAI the most straightforward way to combine **live suggestions**, **structured notes**, **tool use**, and **high-context post-call summarization** under one provider. citeturn35view0turn35view1turn35view4turn37view0turn37view1turn36search11turn36search1turn36search5

**Anthropic Claude API** is especially strong for **long-context analysis, structured note generation, and tool-based assistants**. Anthropic’s docs explicitly document **SSE streaming**, **tool use**, **structured outputs**, and **context windows up to 1M tokens** on higher-end Claude models, with model documentation also describing comparative latency tiers such as **fast** and **fastest**. Anthropic additionally documents **fine-grained tool streaming** to reduce latency when sending large tool parameters. The main limitation for your exact product scope is audio: the official pages reviewed here emphasize text, images, PDFs, tools, and structured outputs, while Anthropic’s OpenAI SDK compatibility page explicitly says **audio input is not supported** in that compatibility layer. In product terms, Claude is an excellent **analysis/summarization lane**, but not the cleanest first pick for your **live meeting-audio lane**. citeturn7view3turn7view4turn9view2turn9view3turn7view5

## Open-model hosts and local backends

**Groq** is attractive when your priority is **speed** rather than maximum feature uniformity. Groq documents an **OpenAI-compatible** API surface, a supported-models catalog that publishes **token speeds** and context windows, and dedicated **speech-to-text** and **text-to-speech** endpoints. That makes Groq especially interesting if your meeting assistant uses a split architecture such as **STT on one service, reasoning on another**, or if you want ultra-fast open-weight models for suggestion generation. The key caveat is that Groq’s **Structured Outputs** docs explicitly say that **streaming and tool use are not currently supported with Structured Outputs**, which is exactly the kind of provider-specific edge case that can break an overly generic abstraction. citeturn18view0turn18view1turn18view2turn18view3

**Together AI** is broader and more flexible than Groq if you want access to many open-source models while still keeping a hosted API. Together documents **OpenAI compatibility**, **streaming**, **function calling**, **structured outputs** on supported models, a serverless model catalog with **context length** and feature columns, and both **batch** and **real-time audio transcription** plus **text-to-speech**. In other words, Together can cover a lot of ground for a “users select any supported open model” story. The catch is that capability is **highly model-specific** rather than uniformly platform-wide: you must query or hardcode per-model support instead of assuming that “Together supports X” means every model does. citeturn18view4turn18view5turn18view6turn19search0turn19search2turn19search5turn20search1turn20search5turn20search13

**OpenRouter** is best understood as a **router and normalization layer**, not as a single model family. Its docs say it provides **one API for hundreds of models**, supports **streaming**, **standardized tool calling**, **structured outputs for compatible models**, **multimodal input/output including audio**, and **provider routing** across upstreams. It also documents a real **BYOK** feature at the OpenRouter workspace level, where your OpenRouter workspace can preferentially route to your own **Bedrock, Vertex, or Anthropic** keys before falling back to OpenRouter’s shared capacity. This is powerful for demos where “choose any model” is the point. The important caveat is that **model and provider compatibility still matters**: OpenRouter can normalize the request shape, but it cannot magically make every upstream model equally good at tools, structured output, or audio. citeturn18view7turn18view8turn18view9turn18view10turn18view11turn18view12turn18view13turn22search0

**Ollama** is a strong privacy-first local option. Its official docs cover **OpenAI compatibility**, **tool calling**, **structured outputs**, **vision/image input**, and configurable **context length**. Ollama’s context-length docs explicitly tie defaults to available VRAM, with examples ranging from **4k** to **256k** context by hardware class, and allow developers to increase context length when hardware permits. This makes Ollama a good fit if you want a “bring your own local model” mode for privacy-sensitive users or offline demos. The limitation is that the reviewed Ollama docs are centered on **local text/image inference** and compatibility layers, not on a first-class meeting-voice stack comparable to OpenAI Realtime or Gemini Live. In practice, that means Ollama works best as the **LLM lane**, while transcription and audio I/O likely come from somewhere else. citeturn26view0turn26view1turn26view2turn26view3turn26view4turn23search11

**LM Studio** plays a similar role, but with a particularly explicit local-server and compatibility story. LM Studio’s docs emphasize a **local API server** with **OpenAI-compatible** and **Anthropic-compatible** endpoints, **tool use**, **structured output**, **stateful chats**, model management, and configurable **context size** per model. Its tool-use docs also make an important point that is useful for your abstraction design: LM Studio says **all models support at least some degree of tool use**, but quality differs between **native** and **default** support. That is a good reminder that “tool calling supported” is not binary in practice; model template quality matters. Like Ollama, LM Studio is highly viable as a **local provider target**, but the reviewed docs do not present it as a dedicated live meeting-audio platform. citeturn26view5turn26view6turn26view7turn26view8turn26view9turn26view10turn26view11

There are three defensible architectural viewpoints here. The **mainstream commercial view** is to start with **OpenAI or Gemini** because realtime voice is first-class. A **router-first view** prefers **OpenRouter** because model choice and fallback are the product’s value proposition. A **privacy-first minority view** prefers **Ollama or LM Studio** plus a separate speech stack so users can keep inference local. None of these views is irrational; they optimize for different outcomes. For a graduation project, however, the most reliable path is usually **commercial realtime first, open/local optional**. citeturn35view4turn11view1turn18view7turn18view9turn26view6turn26view7

## GitHub Copilot and Codex

**GitHub Copilot can no longer be dismissed as “single-model only,”** because GitHub now documents **supported AI models in Copilot**, model choice in Copilot clients, **Copilot SDK**, **Copilot CLI BYOK**, and **enterprise Copilot BYOK**. GitHub’s BYOK docs say Copilot SDK BYOK can use **OpenAI, Azure OpenAI / Azure AI Foundry, Anthropic, Ollama, Microsoft Foundry Local, and other OpenAI-compatible endpoints**, and Copilot CLI BYOK explicitly supports **OpenAI-compatible endpoints, Azure OpenAI, or Anthropic**, including **local Ollama**. GitHub’s enterprise Copilot BYOK docs also say admins can attach provider keys so teams can use preferred LLM providers with **Copilot Chat, Copilot CLI, and VS Code**. Copilot’s model reference further documents that supported model availability depends on **plan and client**, and that the set changes over time. citeturn28view2turn28view3turn28view7turn28view8turn32view1

The reason I would still **not** make GitHub Copilot the default backend for your macOS meeting assistant is scope boundary, not capability denial. GitHub’s own docs define **Copilot integrations** as ways to trigger **Copilot cloud agent** from tools such as **Teams, Slack, Linear, Azure Boards, and Jira**. GitHub’s docs define **custom agents** as Markdown agent profiles that specify **prompts, tools, and MCP servers** for Copilot workflows. GitHub’s **cloud agent API** is documented as an **organization** feature for **Copilot Business or Copilot Enterprise**, not as a public raw chat-completions endpoint for consumer apps. And GitHub’s **local CLI with Copilot SDK** docs explicitly list limitations such as **single-user**, **local-only**, **no multi-tenant**, and required prior CLI sign-in. GitHub also says the SDK communicates with Copilot CLI over **JSON-RPC**, and many interactive CLI features are not exposed programmatically. That means Copilot is real, but it is still a **Copilot product surface** with product-scoped APIs and preview features, not the cleanest generic backend contract for a multi-user meeting tool. citeturn32view0turn28view5turn28view6turn34view1turn34view2turn28view2turn28view8

**OpenAI Codex should be treated separately from GitHub Copilot.** OpenAI’s Codex docs describe **Codex CLI**, **Codex app**, **Codex web**, and Codex models as **coding agents**. Codex supports **ChatGPT sign-in** or **API-key authentication**, and the advanced config docs describe **custom model providers** with configurable base URLs and authentication. The Codex model docs also show that **Codex-branded models such as gpt-5.3-codex have API access**, and Codex can point to any model/provider that supports **Chat Completions or Responses APIs**. But OpenAI’s own `codex-mini-latest` docs say that model is **specifically optimized for Codex CLI**, and for direct API use OpenAI recommends starting with **gpt-4.1**. In your project, that means Codex is technically feasible, but it is **problem-misaligned** unless you want a side feature related to coding, repo analysis, or developer workflows. It is not the natural default for live meeting assistance. citeturn30view4turn30view1turn30view0turn30view2turn30view3

There is also a **licensing and data-governance reason** to be cautious with Copilot-based routes for meeting data. GitHub’s Terms of Service say GitHub does not claim ownership of your input or output, but for **AI Features** GitHub also says that individual-license users grant GitHub and its affiliates a license to collect and use inputs and outputs to **develop, train, and improve** AI systems unless the user opts out or is governed by a customer agreement or volume licensing agreement. ## BYOK and provider abstraction

The most important architecture lesson from the provider docs is that you should **not** build a fake universal API that erases all provider differences. OpenAI has **Responses**, **WebSocket mode**, and a separate **audio/realtime** story. Gemini has **standard**, **streaming**, and **Live API** paths. Anthropic has **Messages-style streaming**, **fine-grained tool streaming**, and huge contexts. Groq’s **Structured Outputs** cannot currently be combined with **streaming** or **tool use**. OpenRouter can normalize request shape, but actual support remains **upstream-model dependent**. GitHub Copilot SDK is not a raw network API at all; in one documented mode it is literally a client that talks to **Copilot CLI over JSON-RPC**. A good abstraction therefore has to be **capability-aware**, not purely provider-name-aware. citeturn35view4turn11view1turn7view3turn7view4turn18view2turn18view10turn18view12turn34view1

For your app, the cleanest design is to separate three contracts. The first is an **LLM response contract** for chat, suggestions, and summaries. The second is an **audio contract** for transcription, speech-to-speech, or TTS/STT services. The third is a **capability registry** that tells the UI and orchestration layer whether a chosen `(provider, model)` pair supports **streaming**, **tool calling**, **JSON-schema output**, **audio input**, **audio output**, **long context**, and any special caveats such as “structured+streaming unsupported.” That registry is what should drive whether the “What should I say?” button can stream partial suggestions, whether “Follow-up questions” can use tools, and whether post-call notes can be emitted as validated JSON. citeturn37view0turn11view2turn18view2turn19search0turn26view8turn26view9

A pragmatic implementation strategy is to use **native adapters** where provider-specific features matter, and an **OpenAI-compatible adapter** where they do not. In practice, I would make **OpenAI**, **Gemini**, and **Anthropic** native adapters because their best features are not identical. I would then make one generic **OpenAI-compatible adapter** for **Groq, Together, OpenRouter, Ollama, and LM Studio**, because all of them document either direct OpenAI compatibility or OpenAI-like request shapes. This gives you broad provider coverage without pretending that every endpoint really behaves the same. citeturn18view0turn18view6turn18view7turn26view0turn26view7turn30view0

BYOK itself should also be modeled in more than one way. A **direct BYOK** path sends the user’s key to the provider’s endpoint. A **router BYOK** path lets the user give you an **OpenRouter key**, while OpenRouter can itself route to workspace-level downstream BYOK providers. A **local-provider path** may need **no cloud key at all**, just a local base URL and model identifier for Ollama or LM Studio. And **GitHub/Codex auth should remain a separate special case**, because GitHub’s BYOK is preview-scoped to Copilot surfaces and OpenAI Codex supports different auth/product flows. Trying to flatten those into one “enter any token here” UX usually confuses both product semantics and support obligations. citeturn18view8turn26view6turn26view7turn28view2turn28view3turn30view1

## Recommended stack for your capstone

If this were my project, I would scope the shipped demo around **one excellent realtime stack plus optional extensibility**, not around perfect support for every provider on day one. The most convincing baseline is either **OpenAI-first** or **Gemini-first**. OpenAI gives you one of the cleanest unified stories across **live audio**, **function calling**, **streaming**, **structured outputs**, and **large-context follow-up analysis**. Gemini gives you a similarly compelling story with a very strong **Live API**, built-in **audio transcriptions**, **tool use**, and **1M-token** long-context text models. Either one can power the live “What should I say?” companion and the typed meeting-notes output that your UI needs. citeturn35view0turn35view1turn35view4turn37view0turn37view1turn11view1turn11view2turn11view5turn14view0

My second recommendation would be to add **Anthropic** as a non-default but high-value provider for **meeting-note generation, analysis, and action-item extraction**, especially if you want users to compare outputs across vendors or prioritize long-context document reasoning. Anthropic’s structured outputs and large context windows make it a strong fit for post-call analysis, even if it is not the cleanest primary choice for live audio capture. citeturn7view4turn9view3turn7view5

My third recommendation would be a single **advanced OpenAI-compatible adapter** that supports **Groq, Together, OpenRouter, Ollama, and LM Studio**. This is where you satisfy the “users can choose their own model” requirement at scale. OpenRouter gives you breadth and routing. Groq gives you speed. Together gives you hosted open-model variety plus STT/TTS. Ollama and LM Studio give you privacy-first local modes. That one adapter can turn your project from a single-vendor demo into a real **provider-agnostic system**, while still keeping native realtime/audio logic in the vendors that deserve it. citeturn18view7turn18view9turn18view0turn20search3turn26view6turn26view7

What I would **not** do is center the architecture on **GitHub Copilot**. You can absolutely experiment with **Copilot SDK** or **Copilot CLI BYOK** as an advanced integration, especially if your project audience is developers and you want a “bring your own Copilot” mode. But GitHub’s own docs show that Copilot is still a **Copilot-shaped surface**—with preview-scoped SDKs, CLI coupling, organizational cloud-agent APIs, and product-specific constraints—rather than the simplest generic foundation for a meeting assistant. Likewise, I would treat **OpenAI Codex** as optional and only if you explicitly want a coding-agent mode beside the meeting features. citeturn28view2turn28view6turn34view1turn34view2turn30view2turn30view3

The shortest path to a strong result is therefore this: **native OpenAI or Gemini for live meeting UX, Anthropic for optional analysis, one OpenAI-compatible adapter for model-choice breadth, and local Ollama/LM Studio support as a privacy mode**. That gives you a capstone that is both academically interesting and product-credible: it demonstrates live AI assistance, typed action-item extraction, provider abstraction, BYOK, and local-model extensibility without forcing GitHub Copilot or Codex into a role they were not primarily designed to fill. citeturn35view4turn37view0turn11view1turn7view4turn18view7turn26view6
